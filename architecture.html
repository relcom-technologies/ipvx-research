Как устроен IPvX

Четыре части: реестр, пакетный слой, имена и выбор маршрута. Ниже — что из них уже реализовано и проверено, а затем исторический прототип, на котором измерялась доставка без IP.

Реестр: адрес из блокчейна

В исходных статьях адрес IPvX записан тремя частями: сторона подключения, сущность (NFT) и правило соединения (смарт-контракт). Его не выдаёт цепочка ICANN → RIR → провайдер: владение и правила записаны в реестре, который может проверить любой.

В BCP 0.2 это три контракта. NodeRegistry связывает NFT узла с владельцем и ключами. TransitPolicy и ConnectionPolicy задают, через кого можно пройти и с кем можно соединиться; правило действует, только когда согласны обе стороны. Пакет BCP несёт владельца, NFT и правило соединения получателя.

Опыт REG-001 проверил эти контракты на тестовой цепочке Sepolia: чужой владелец не может изменить узел, а изменение становится действующим для узлов через 14–19 минут — после финализации блока. Итоги REG-001 →

Реализовано в коде

Формат пакетов, NodeRegistry, TransitPolicy, ConnectionPolicy, EL/CL-адаптер и связь с ядром. Чтения контрактов привязаны к одному финализированному blockHash.

Проверено офлайн

77 тестов runner и 14 проверок плана. Временные ключи, EVM в памяти, синтетические заголовки и memory ports; это не измерение сети или финальности цепочки.

Имена: резолвер IRS

Во второй исходной статье имена берутся из реестра, а не из иерархии DNS. Резолвер IRS отвечает на обычные запросы имён, но данные берёт из блокчейна. Имена плоские и не зависят от корневой зоны ICANN; в статье показана рабочая зона iedn.ipvx.

В исследовании этот трек ещё не начат. Протокол NAME-001 будет написан после опыта NET-001, когда реестр уже будет давать узлам настоящее состояние.

Выбор маршрута

Договоры между NFT задают разрешённые пути, но не выбирают среди них лучший. Выбор можно делать по цене, задержке или условиям договора; в исходной статье эту задачу поручают ИИ. В исследовании выбор маршрута по договорам ещё не проверялся.

Где остаётся IP

IPvX заменяет IP-адресацию и DNS, а не надстраивается над ними. На переходном этапе пакеты IPvX можно перевозить через существующий IP; тогда IP — только носитель, а не часть адреса.

Сейчас IP остаётся там, где без него пока не обойтись: этот сайт, управление машинами стенда, установка моделей и чтение реестра с узла Ethereum. В опытах с доставкой кадры между узлами идут без IP. Если соединить площадки IP-туннелем, это будет переходный режим, и он не докажет отказ от IP в нижележащей сети.

Как устроен проверенный стенд

Три гостевые ОС на разных физических машинах. У A и B работают локальные языковые модели; R1 пересылает сообщения между ними.

Исследовательская визуализация записанного опыта. Это не прямой эфир; темп анимации условный.

Режим: записанный strict-LLM-опыт · A–R1–B · 3 гостя / 3 физических хоста · 2 локальные модели.

Отдельно: живой mesh — 5 ВМ / 3 физических хоста, без LLM, с административным IP в ОС. У обоих нативные данные и маршруты идут в Ethernet 0x88B5; веб-панель и управление используют HTTPS/IP. Открыть живой mesh и его версию.

Внешнее управление, запуск виртуальных машин и этот сайт используют IP. Общая физическая сеть также переносит управляющий IP-трафик. Нативная доставка внутри гостевых ОС не использует IP или DNS.

  1. A готовит задачу

    Модель A готовит ответ. IPvX-служба адресует сообщение ID агента B, подписывает и шифрует его.

  2. Запрос проходит через R1

    A отправляет кадр соседу R1; R1 выбирает следующий переход к B. Квитанция подтверждает приём, а не правильность результата.

  3. B проверяет и отвечает

    Модель B получает задачу и формирует рецензию. Ответ отправляется отдельным сообщением через R1 обратно к A.

  4. A формирует итог

    Модель A использует рецензию для итогового ответа. Оценка поля решения совпала с эталоном в двух из четырёх задач.

Что подтверждено

4 задачи и 48 подтверждённых доставок в нативном режиме: 40 эхо-проверок и 8 сообщений по задачам. IP-контроль использовал те же прикладные переходы.

Время на каждом переходе, ожидание в очереди и причина выбора маршрута в опубликованной записи отсутствуют. Показ пути не измеряет их.

Внешние сети, открытый допуск, масштабная маршрутизация и физические серверы без IP на bare metal остаются отдельными непроверенными задачами.

Уровни исторического прототипа

  1. Идентичность

    Узел сам создаёт ключи. Его ID вычисляется из открытого ключа и сохраняется при смене сетевого положения. Доверие и допуск задаются отдельно.

  2. Задача

    Агенты обмениваются структурированными заданиями, доказательствами и результатами. Для этого им не нужны страницы сайтов. Совместимость форматов задач всё равно необходима.

  3. Маршрутизация

    Узел получает подписанные объявления соседей и выбирает следующий переход из локальной таблицы. Центральный наблюдатель не передаёт задания и не назначает маршруты.

  4. Доставка

    В нативном опыте пакет превращается в кадры Ethernet с EtherType 0x88B5. MAC обозначает соседа на локальном канале; ID обозначает конечного агента.

От прототипа к BCP

В историческом прототипе ID создаётся из ключа. В BCP NodeRegistry связывает NFT-идентификатор с владельцем и ключами, а TransitPolicy и ConnectionPolicy задают разрешённые пути. Это разные модели допуска; их результаты не подменяют друг друга. Имён в BCP 0.2 пока нет: их место займёт резолвер IRS.

Узел без TCP/IP: проверенный опыт

В завершённом опыте локальные модели работали в целых гостевых ОС без INET и IPv6 на разных физических хостах. Внутри гостей наблюдались кадры Ethernet, а управление внешними машинами сохраняло IP. Фактическая подложка между гипервизорами отдельно не подтверждена их конфигурацией.
