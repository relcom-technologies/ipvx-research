# BCP 0.2-LC: чтение реестра через проверяющий лёгкий клиент

Статус: **Draft, предложен 5 ноября 2026 года**. Автор: Claude Code
(`claude-code-assistant`) по решению владельца не выделять отдельную ВМ под полный
узел Sepolia. Документ дополняет [BCP 0.2](../bcp-0.2/README.md), не меняя его файлов:
режим validated-node остаётся, рядом появляется второй режим доверия.
Машиночитаемая часть — [profile.json](profile.json).

## 1. Зачем

Режим V требовал собственную пару Geth + Lighthouse: около 1 ТБ SSD, 4 ядра и 16 ГБ
памяти только ради чтения трёх контрактов. При этом адаптер validated-node сам не
проверяет ни подписи консенсуса (BLS), ни доказательства хранилища: он доверяет своему
узлу ([adapters/bcp02](../../../adapters/bcp02/README.md)). Лёгкий клиент проверяет то
и другое и почти ничего не хранит.

## 2. Режим verified-light-client

- Байт `trust_mode` в профиле равен **2** (у validated-node — 1). Остальные поля и
  константы BCP 0.2 не меняются, поэтому ID профиля отличается только этим байтом.
  Узлы в разных режимах не принимают кадры друг друга.
- Эталонный клиент — **Helios 0.12.0** (a16z, commit
  `2af9b41887e069144ee56cd710f3ddca195473f8`), сеть Sepolia в нём встроена.
- Helios проверяет подписи комитета синхронизации от закреплённой контрольной точки
  (weak subjectivity) и каждое значение счёта, хранилища и кода по доказательствам
  Меркла от проверенного корня состояния. Публичный RPC подделать ответ не может, он
  может только не ответить.
- Адаптер (`adapters/bcp02/light.py`) ходит к Helios только по loopback и проверяет:
  chain ID и точную версию клиента; что Helios не синхронизируется (он отвечает так,
  только пока его проверенная голова моложе 60 с); финализированный блок;
  происхождение от сохранённой точки одним запросом блока по номеру, который Helios
  проверяет по истории EIP-2935; коды контрактов, ABI и чтение всех значений по одному
  хешу блока, как в режиме V.

## 3. Что обязан сделать оператор

- Запускать Helios с **явной** контрольной точкой не старше 14 дней,
  `strict_checkpoint_age = true` и без внешних источников контрольных точек
  (`load_external_fallback = false`): иначе точку доверия выбирает чужой сервис.
- Слушать только `127.0.0.1`; записать SHA-256 установленного бинарного файла.
- Указать RPC исполнения, отдающий `eth_getProof` на финализированном блоке, и
  консенсусный сервис с API лёгкого клиента.
- Читать не реже раза в ~27 часов: сохранённая точка старше 8191 блока недоступна, и
  тогда нужна новая начальная точка (`STATE_UNAVAILABLE`, не конфликт).

## 5. Границы

- Доверие переходит от полного набора валидаторов к комитету синхронизации (512
  валидаторов, нужно 2/3 подписей). Набор валидаторов Sepolia и так закрытый.
- Старые снимки недоступны: S1–S3 REG-001 старше окна. R1 закрывается чтением
  текущего состояния контрактов прогона 6, которое должно совпасть с S4.
- Helios не установлен и не запускался; совместимость адаптера с ним проверена только
  на фикстурах. Независимого аудита Helios с нашей стороны нет.
- Сам лёгкий клиент ходит к RPC по IP; это переходный носитель, как и в режиме V.
