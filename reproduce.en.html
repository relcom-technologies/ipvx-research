BCP 0.2

BCP 0.2 is the IPvX packet layer and registry. The registry contracts were tested on the live Sepolia chain: REG-001 ran in read mode Q, and R1 was closed on 2026-11-06 by the REG-001-LC light-client read on its replacement criterion, the current state; the S1–S3 values remain mode Q observations. Packet delivery driven by the registry (NET-001) has not run.

Status snapshot: 2026-11-06

Implemented in code

Packet format, NodeRegistry, TransitPolicy, ConnectionPolicy, the EL/CL adapter and core integration. Contract reads are pinned to one finalized blockHash.

Checked offline

77 runner tests and 14 plan checks. Temporary keys, an in-memory EVM, synthetic headers and memory ports; no network or chain-finality measurement.

Next network experiment

NET-001: the protocol is accepted in two variants, on test state and on live registry state; neither has run. The live variant reads the registry through the Helios light client: mode LC replaced mode V on 2026-11-05, so no own Sepolia node is needed. Helios is not running on the stand: the temporary client used for the read was removed. The separate NET-001 stand VM is not allocated, and the snapshot refresh rule in NET-001-L is an open condition. Launch admission is closed.

Experiment package

LLM comparison protocol, native-experiment summary, simulation parameters and data provenance are available without signing in.

The public archive of the early native prototype contains source and four PCAPs: three guests on one CI host, SHA-256 without LLMs. The full Lab platform and original captures of the physical strict-LLM experiment remain in a private repository. Its sanitized public projection cannot reverify the original bytes. Access can be proposed for discussion through a public proposal; it is not granted automatically.

Requirements for your own run

  1. Pin the code version, model weights and dependencies by hash.
  2. Use separate Linux machines or explicitly state that nodes are namespaces on one host.
  3. Separate IP management from the chosen task channel; do not conceal an IP underlay between sites.
  4. Publish fresh model calls, errors, retries, paths and result verification.
  5. Repeat over ordinary IP with the same parameters, showing the hop count and trial order.
