RFC-0001 — Identität und authentifizierte Nachrichten

IPvX-Arbeitsdokument · Entwurf · offen zur Diskussion

RFC-DiskussionOriginaltext

Status: Entwurf · experimentelles IPvX-Forschungsdokument · kein IETF-RFC.

Problem

Ein Agent benötigt eine stabile Identität, die weder von einem DNS-Namen noch von seiner aktuellen Transportadresse abhängt.

Vorgeschlagener Mechanismus

Ein Agent erzeugt lokal einen Ed25519-Signaturschlüssel und einen separaten X25519-Verschlüsselungsschlüssel. Seine ID wird aus dem öffentlichen Signaturschlüssel abgeleitet. Nachbarn werden ausdrücklich anhand ihres öffentlichen Schlüssels zugelassen. Ein signierter Kontakt bindet die ID an einen aktuellen Kanalendpunkt, eine Version und eine kurze Gültigkeitsdauer. Ein Kontakt ist eine Aussage seines Eigentümers; er gewährt für sich allein keine Netzzulassung.

Aufgaben binden Sender, Empfänger, Nachrichten-ID, Ausgabe-/Ablaufzeit und Chiffretext-Hash. Das Ziel entschlüsselt und prüft die Aufgabe, speichert eine Bestätigung dauerhaft und nutzt einen Anfrage-Hash, um die Wiederverwendung derselben ID für andere Inhalte abzulehnen. Die Bestätigung der Warteschlangenannahme ist etwas anderes als der Abschluss einer Modellinferenz.

Implementierte Nachweise

Das begrenzte Labor implementiert native Ethernet-Frames mit experimentellem EtherType 0x88B5, Fragmentierung, Hop-Nachweisen, signierten Routenankündigungen und verschlüsselten Aufgaben-/Bestätigungsnutzlasten. MAC-Adressen sind lokale Kanallokatoren. IDs aus öffentlichen Schlüsseln sind nicht automatisch global routbare Adressen.

Offene Fragen

Schlüsselwiederherstellung und -rotation; Verhalten bei doppelten IDs während Partitionen; Sybil-resistente Zulassung; Metadatenschutz; Replay-/Ressourcenerschöpfungsangriffe; Austauschbarkeit kryptografischer Algorithmen; dauerhafte Genau-einmal-Semantik der Anwendung nach Abstürzen. Die aktuelle Deduplizierung von Bestätigungen beweist keine universelle exakt einmalige Geschäftsausführung.

Prüfkriterien

Paketschema, deterministische Testvektoren, implementierungsübergreifende Signaturprüfung und Fehlerfälle veröffentlichen. Die bestehende Implementierung bleibt eine Forschungsbasis, bis diese Kriterien und die Governance-Abstimmung abgeschlossen sind.

Originaldokument

Status: Draft · experimental IPvX research document · not an IETF RFC.

Problem

An agent needs a stable identity that does not depend on a DNS name or its current transport address.

Proposed mechanism

An agent generates an Ed25519 signing key and a separate X25519 encryption key locally. Its ID is derived from the signing public key. Neighbors are explicitly admitted by public key. A signed contact binds the ID to a current link endpoint, version and short expiry. A contact is an assertion by its owner; it does not itself grant network admission.

Tasks bind sender, recipient, message ID, issuance/expiry and ciphertext hash. The destination decrypts and verifies the task, persists a receipt, and uses a request hash to reject reuse of the same ID for different content. Acknowledging admission to a queue is different from completing a model inference.

Implemented evidence

The bounded lab implements native Ethernet frames using experimental EtherType 0x88B5, fragmentation, hop proofs, signed route advertisements and encrypted task/receipt payloads. MAC addresses are local link locators. Public-key IDs are not automatically globally routable addresses.

Unresolved

Key recovery and rotation; duplicate-ID behavior during partitions; anti-Sybil admission; metadata privacy; replay/resource exhaustion; cryptographic algorithm agility; persistent application exactly-once semantics after crashes. Current receipt deduplication does not prove universal exactly-once business execution.

Review criteria

Publish a packet schema, deterministic test vectors, cross-implementation signature verification and failure cases. The existing implementation remains a research baseline until these criteria and the governance vote are completed.
