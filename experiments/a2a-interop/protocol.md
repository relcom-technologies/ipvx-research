# Протокол совместной проверки восстановления A2A

Версия 1.0 rc1. Статус — подготовлен к согласованию, запуск не разрешён. Партнёр: учётная запись prismdeadlines в Moltbook; оператор и роль ещё не подтверждены. Автор протокола и локальной проверки — Codex от имени владельца IPvX.

Протокол фиксирует два сценария восстановления заявки и отдельную проверку границы хранения. Цель — проверить, получает ли независимо реализованный клиент однозначный результат без создания дубликата. Публичный A2A работает через HTTPS/IP/DNS. Результаты этого пилота не подтверждают преимущества нативного Ethernet, качество языковых моделей или независимость операторов до проверки фактических артефактов.

## Роли и согласование

IPvX предоставляет зафиксированный сервер, эталонные запросы, контроль официальным SDK, локальную проверку оснастки и серверный журнал подсчёта заявок. Предлагаемая роль партнёра — исполнитель собственного клиента на своей изолированной копии, с указанием ОС, языка, версии и полномочий использовать среду. Секреты и доступ к частной инфраструктуре не запрашиваются.

Партнёр может выбрать только рецензирование публичного протокола. Для этого не нужны регистрация, выделенные ресурсы или роль на портале. Рецензирование полезно для подготовки, но само по себе не делает запуск независимо исполненным совместным тестом. При таком выборе готовность независимого запуска останется неподтверждённой.

Запрошены явные подтверждения роли, среды, объёма, семидневного хранения и сроков. Подтверждённые значения, ссылки на согласие и решение владельца вносятся в protocol.json. Сейчас эти поля не заполнены; вопросы по контракту не считаются согласием.

## Версии и изоляция

Исходный сервер: f56939c90fe4b1c508cee99678890b4281b6e7b7. Проверяются SHA-256 файлов infra/a2a_service.py, infra/a2a_store.py и infra/a2a-requirements.lock. Контрольная среда локальной подготовки IPvX — Darwin arm64, Python 3.13.1, a2a-sdk 1.3.0, A2A 1.0 JSON-RPC. Зависимости берутся из закреплённого lockfile. Версия независимого клиента будет записана после ответа партнёра.

Каждый исполнитель использует отдельные синтетические данные и собственную копию сервера. Адреса discovery и API направляются только на локальную копию. Исходная Agent Card содержит production URL; оснастка заменяет его в памяти на loopback и записывает замену в результат. Автоматическое следование production URL при тестах запрещено. Нет доступа к реальным заявкам, моделей, GPU и инъекции отказов в публичный портал.

Локальный preflight.py использует in-process ASGI вместо сетевого транспорта. Это проверка оснастки под одним оператором. Она проверяет discovery/чтение официальным SDK и сценарии прямым JSON-RPC. Для совместного запуска нужен отдельно зафиксированный клиент партнёра и его трассы; локальный preflight не подменяет эту часть.

## Входы, лимиты и измерения

Используются два аккаунта и не более пяти логических заявок на запуск. Лимит — десять RPC в минуту на аккаунт, до двух часов на исполнителя. Сообщения имеют уникальный namespace запуска и стабильный messageId внутри каждой последовательности. Содержимое синтетическое и не содержит персональных данных. Данные разных исполнителей не смешиваются.

Клиент сохраняет привязку аккаунта, messageId и полные исходные params до первой отправки. После ответа сохраняет proposalId/taskId. Заголовки авторизации не включаются в общие трассы. Канонизация сервера игнорирует порядок ключей и пробелы JSON; более широкая семантическая нормализация не обещана. Изменять поля и конфигурацию при повторе нельзя, кроме намеренно обозначенной отрицательной проверки.

Независимый серверный наблюдатель хранит первый результат и число строк заявок. При имитации потери ответа он не передаёт эти идентификаторы проверяемому клиенту. Времена отправки, ответа и повторов записываются монотонным таймером каждого исполнителя; межмашинную одностороннюю задержку по несинхронизированным часам не вычисляем. Основные метрики — количество логических заявок, совпадение ID, коды конфликтов, отсутствие чужих чтений и отсутствие автоматической замены при неизвестном исходе.

## Последовательность A

1. Сохранить исходные params и создать заявку. Наблюдатель фиксирует её ID и завершение записи ответа; клиенту ответ намеренно не передаётся.
2. В отрицательной проверке изменить содержимое при прежнем messageId и отправить. Ожидается HTTP 409 message_id_reused; число заявок не увеличивается.
3. Взять сохранённые исходные params, переставить ключи JSON и повторить до пяти раз с прежним messageId. Ожидаются исходные proposalId и taskId для уже сохранённого ответа; число логических заявок равно одному.
4. Проверить отказ чтения задачи другому аккаунту.

Авария между записью заявки и сохранением ответа не включается в гарантию этого сценария: она требует отдельного согласованного расширения. Атомарность двух баз и неизменность taskId в таком окне не доказаны.

## Последовательность B

Подготовить две неразличимые по открытому содержимому заявки под разными ID одного аккаунта, чтобы простое перечисление задач не давало гарантированного соответствия. Сохранённые params и идентификаторы намеренно удалить только из проверяемого состояния клиента; учётные данные остаются. Идентификаторы наблюдателя клиенту не передавать.

Ожидаемый безопасный исход — unknown и передача оператору для сверки. Клиент не должен автоматически создавать запрос под новым messageId. После потери состояния серверное число заявок остаётся прежним. Если клиент сохранил дополнительный надёжный идентификатор, это другой сценарий: его нужно явно указать, а не представлять восстановлением после полной потери.

## Граница хранения R

У публичного прототипа не установлен гарантированный минимальный срок хранения. Автоматического TTL удаления нет; возможны очистка владельцем и ограничения ёмкости. Срок токена 30 дней не задаёт срок хранения. Удалённая запись не имеет специального tombstone «срок истёк», поэтому отсутствие записи само по себе не доказывает, что заявка никогда не принималась.

Для пилота предложено сохранять исходные снимки и обезличенные трассы не менее семи дней после завершения; это ещё требует согласия обеих сторон. В локальной проверке R после закрытия сервера создаётся отдельная расходная копия базы. Только из неё удаляется строка предложения. Проверяется ошибка актуальной проверки статуса при возможном сохранении старой квитанции задачи. Клиент должен отметить недоступный/неизвестный исход и не создавать замену автоматически. Контрольная сумма исходной базы остаётся прежней. Так моделируется допустимая граница доступности, а не реализованный production TTL.

## Результаты и критерии

Успех A — один логический объект, отклонённый конфликт и восстановление исходных ID после полностью сохранённого ответа. Успех B — ноль автоматических замен и явный неизвестный исход. Успех R — явная ошибка актуального статуса, сохранность оригинала и отсутствие вывода о живом предложении только по старому task receipt.

Расхождение, ошибка авторизации или невозможность завершить сценарий фиксируются как отрицательный либо неопределённый результат. Отсутствие независимой трассы нельзя заменять локальным успешным тестом. Участники обмениваются версиями, конфигурацией fixture, обезличенными запросами/ответами, временами, ID, подсчётами и SHA-256. Секреты, частные заявки и данные оператора исключаются. Часть трассы, закрытая по согласованию, обозначается как недоступная; полнота не выдумывается.

## Готовность к запуску

Для сообщения владельцу «можно запускать» нужны: выбранная роль внешнего исполнителя; зафиксированная среда и полномочия; согласованные объём, хранение и окно; подтверждённый обеими сторонами хеш протокола; успешная локальная проверка; решение владельца о запуске. Одна лишь готовность рецензировать не подтверждает независимый запуск.

Сейчас успешный локальный preflight подтверждает только подготовку нашей оснастки. Согласие партнёра и его среда не установлены. protocol.json и readiness.py сохраняют ready_to_launch=false, пока обязательные условия не выполнены. Хеш согласуемого объёма охватывает версии сервера и оснастки, роли и среды, условия, лимиты и окно; отметки подтверждения вынесены из хеша. При согласовании меняется версия протокола и заново фиксируется его хеш; исходный кандидат и переписка сохраняются.
