# IPVX-BCP02-NET-001-L — Ethernet-опыт на живом состоянии реестра

Версия **0.1, proposed / NOT_RUN**. Автор и регистратор: `claude-code-assistant`.
База исходников: `45da649059ab25e7ac330e31c14aa93f9846dc98` (после результатов REG-001).
Это протокол, а не запуск: ни ВМ, ни узла Sepolia, ни транзакций, ни кадров.
Принятие PR не разрешает запуск; нужны отдельные решения владельца (раздел 6).

## 0. Зачем второй вариант NET-001

[NET-001-F](../bcp02-net-001/README.md) проверяет доставку BCP по Ethernet на
**синтетическом** состоянии: ключи и правила узлов приходят из фикстур, финальности нет.
Его пакет закреплён хешами и не меняется. Вариант **L** берёт то же ядро — те же узлы
A—R—B, те же veth, тот же wire 0.2, те же 13 случаев и те же оракулы — и меняет только
источник состояния: ключи узлов и разрешённые пути читаются из **живого реестра в
Sepolia** в финализированном блоке, как требует профиль BCP 0.2.

Это первый опыт, где IPvX работает «в миниатюре» целиком: узлы получают идентичность
и права из блокчейна, а данные идут кадрами 0x88B5 без IP-адресов, маршрутов и DNS
в пространствах имён узлов. [REG-001](../bcp02-reg-001/README.md) показал, что реестр
работает на живой цепочке (R2, R3), и измерил, сколько ждать финализации (R4).

## 1. Что меняется относительно F

| | NET-001-F | NET-001-L |
|---|---|---|
| `state_mode` | `fixture-state-ethernet` | `sepolia-finalized-snapshot` |
| источник состояния | фикстуры, EVM в памяти | реестр Sepolia, режим чтения **LC** ([BCP 0.2-LC](../../docs/proposals/bcp-0.2-light-client/README.md)): лёгкий клиент Helios 0.12.0 на стенде и `lightclient/bcp02/light.py`; до 2026-11-05 здесь был режим V с собственной парой Geth + Lighthouse |
| режим Q (публичные RPC) | — | **запрещён**: профиль не допускает публичные RPC |
| ключи узлов | свежие на прогон, в фикстуре | свежие на прогон, **регистрируются в цепочке** до окна опыта |
| транзакции | 0 | до 24 на прогон (21 до окна, 3 внутри) |
| N06, N07 | смена фикстуры L | настоящие транзакции `setKeys` и `withdraw` |
| N08 | недоступный и устаревший фикстурный провайдер | настоящая блокировка источников лёгкого клиентатора на файрволе стенда |
| окно | 3600 с | 7200 с, из них активных ≤ 1200 с; ожидания финализации отдельно |

Всё остальное — из [protocol.json](../bcp02-net-001/protocol.json) F без изменений.
Отличия в машинном виде — [protocol.json](protocol.json).

## 2. Время: главное следствие REG-001

В F состояние меняется мгновенно, поэтому срок исхода 20 с и 90 с на случай.
В живой цепочке изменение становится действующим для узла только после финализации:
в REG-001 — **от 14,2 до 19,0 минуты, медиана 16,5**. Поэтому:

1. Случаи, меняющие реестр, идут последними, по одному изменению на снимок:
   N07a (отзыв ребра R→B), N07b (отзыв обратного соединения B→A), N06 (смена ключей A).
   Смена ключей A делает недействительными и его рёбра, поэтому она последняя.
2. Сроки 20 с и 90 с отсчитываются от **первого наблюдения узлом** снимка L с этим
   изменением, а не от отправки транзакции. Ожидание финализации ограничено 1500 с
   и в активное время не входит.
3. Новое измерение **L1**: время от транзакции до первого кадра, отклонённого узлом.
   Это практический смысл R4 для сети: как быстро отзыв права реально останавливает
   трафик. Порога нет — это измерение.

**Свежесть.** Профиль требует, чтобы состояние было не старше 1800 с от времени
финализированного заголовка. В REG-001 финализированный блок в момент принятия был уже
старше на 781–792 с, значит, запас — около 17 минут. Читатель обновляет снимок не реже
раза в 300 с. N08 в живом виде: блокировка источников лёгкого клиента даёт `STATE_UNAVAILABLE` при
следующем чтении, а после того как кешированный снимок перешагнёт 1800 с, — `STATE_STALE`.

## 3. Где появляется IP и где его нет

Узлы A, R, B по-прежнему без адресов IPv4/IPv6, маршрутов и сокетов AF_INET; данные
только кадрами 0x88B5. Но состояние нужно откуда-то читать: отдельный процесс
чтения состояния в своём namespace спрашивает лёгкий клиент на loopback, а тот ходит
к публичным RPC Sepolia по HTTPS и проверяет каждый ответ доказательствами. Это и есть переходный носитель из статей: IP перевозит
чтение реестра, а не BCP-кадры. Канал состояния не несёт кадров BCP и полезной
нагрузки; это проверяется по захватам. Поэтому «устройство без IP» этот опыт
не доказывает — только то, что плоскость данных между узлами без IP.

## 4. Последовательность прогона

1. **До окна.** Свежие ключи A, R, B. W1 регистрирует A и R, W2 — B. Рёбра A↔R, R↔B и
   соединения A↔B с согласиями обеих сторон (21 транзакция, исполнитель REG-001 с новой
   последовательностью). Дождаться финализированного снимка C и принять его в режиме LC.
2. **Окно, без изменений реестра:** P01, P02, N01–N05, N09–N11 на снимке C с обновлением
   не реже раза в 300 с.
3. **Изменения реестра:** N07a → ожидание L → проверка; N07b → ожидание → проверка;
   N06 → ожидание → проверка. Для каждого фиксируются все отметки L1.
4. **N08:** блокировка источников лёгкого клиента, `STATE_UNAVAILABLE`, ожидание до `STATE_STALE`.
5. **Сохранение** — как в F, плюс все транзакции, снимки C и L (blockHash, адреса и
   runtime-хеши контрактов) и привязка адаптера без секретов.

Шаги не повторяются автоматически; неудачная транзакция — результат.

## 5. Чего этот опыт не доказывает

- отсутствия IP во всём устройстве: лёгкий клиент использует IP до публичных RPC;
- физического Ethernet между хостами: стенд — одна ВМ с veth;
- независимости операторов: W1 и W2 у одного владельца, узлы у одного оператора;
- полноты финальности сверх границы доверия к собственной паре EL/CL;
- имён (NAME-001) и выбора маршрута ИИ.
