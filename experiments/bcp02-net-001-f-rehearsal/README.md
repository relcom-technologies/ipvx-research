# Репетиция раннера NET-001-F на стенде BCP

**8 ноября 2026 года, исход REHEARSAL_PASS в трёх прогонах из трёх.** Автор и регистратор:
`claude-code-assistant`, по разрешению владельца в чате («Да, репетиция»).
Машиночитаемый итог — [result.json](result.json), исходные отчёты и захваты — в `raw/`,
их хеши — в [SHA256SUMS](SHA256SUMS).

Это **не сетевой опыт**. Сетевой опыт IPVX-BCP02-NET-001-F по-прежнему NOT_RUN:
разрешение на запуск не выписывалось, набор данных не готовился, ядро BCP, ключи прогона
и цепочка не использовались, транзакций ноль.

## Что проверялось

Команда `python3 -m runners.bcp02.cli rehearse` проходит тот же путь в ядре Linux, что и
настоящий прогон, но на синтетических кадрах. Подробно она описана в
[README раннера](../../runners/bcp02/README.md#permit-free-rehearsal).

1. Создаются три namespace и две veth-пары A—R—B без IP-адресов.
2. Запись обоих линков включается до того, как линки поднимаются.
3. Процессы узлов сбрасывают привилегии и включают seccomp, после чего проверяется, что
   новые сокеты и процессы им запрещены.
4. По пути A—R—B и обратно идут кадры 0x88B5 размером 60 и 1514 байт.
5. Аудит `/proc` проверяет каждый процесс, захваты сверяются с ожидаемым набором кадров.
6. После проверки всё убирается.

До сих пор репетиция проходила только в одноразовом Docker-контейнере на aarch64, со
скрытием резервных туннелей ядра и в обход проверки архитектуры x86_64 (HX-0199).
Здесь она впервые прошла на стенде, где будет настоящий прогон, без этих обходов.

## Стенд

`proj-ipvx-bcp-stand`, объявлен в relcom-technologies/relcom-infra#865:

- x86_64, ядро `6.12.105+deb13-cloud-amd64`, Debian 13;
- 2 vCPU, 1974 МиБ памяти;
- Python 3.13.5.

Изменения на хосте:

- установлен пакет `python3-venv`;
- в `/opt/ipvx-bcp/<ревизия>` лежат дерево репозитория и виртуальное окружение;
- до перезагрузки выставлено `net.core.fb_tunnels_only_for_init_net=1`, как требует README
  раннера; модули туннелей не загружены;
- в `/var/lib/ipvx-bcp` остались каталоги отчётов.

## Результат

| | Прогон 1 | Прогон 2 | Прогон 3 |
|---|---|---|---|
| Исход | REHEARSAL_PASS | REHEARSAL_PASS | REHEARSAL_PASS |
| Линк L1: кадры / потери | 4 / 0 | 4 / 0 | 4 / 0 |
| Линк L2: кадры / потери | 4 / 0 | 4 / 0 | 4 / 0 |
| Namespaces после прогона | 0 | 0 | 0 |

У всех пяти процессов (два захвата, A, R, B) после сброса привилегий пустые наборы
capabilities, `NoNewPrivs=1` и `Seccomp=2`. Каждый процесс открыл только объявленные
packet-сокеты: по одному у A, B и захватов, два у R.

Первый прогон занял 0,9 с. Занятая память на хосте выросла с 269 до 328 МиБ. Значит,
2 ГБ хватает на саму репетицию; хватит ли их на настоящий прогон с ядром BCP, это не
показывает.

## Находка: закрепление исходников разошлось с main

Раннер закрепляет хеши 450 файлов репозитория (`runners/bcp02/manifest.json`), и `cli check`
сверяет их перед любым действием. На текущем main `9aeb7a4` проверка заблокирована: после
третьей ревизии раннера изменился 21 файл. Все они относятся к сайту и форуму: `assets/`,
`infra/`, `scripts/build_*`, `DESIGN.md`, `.github/workflows/browser.yml`. Сам код раннера
между `12705b7` и `9aeb7a4` не менялся.

Поэтому репетиция шла на ревизии `12705b7`, слиянии PR72, где закрепление сходится
полностью, а `check` даёт NOT_RUN со `scope_sha256 = 6f2ce257…24bcc1`. README раннера уже
называет это известным пробелом: изменения вне путей раннера ломают закрепление незаметно.
На main по той же причине падают и сверки сохранности `runners/bcp02/preserve.py` и
`experiments/bcp02-net-001/preserve.py`. Они запускаются в CI только на PR, которые трогают
пути раннера или плана, поэтому расхождение пока никто не видел; первый такой PR упадёт.
Перед настоящим прогоном нужно либо заново заморозить manifest на рассмотренной ревизии,
либо сузить закрепление до файлов, от которых зависит прогон. Это решение владельца.

## Ограничения

- Пройдена только «сантехника» ядра. Ядро BCP, цикл `entry` и настоящий узел с ядром Linux
  ещё не встречались; это и будет сам прогон.
- В `bcp/requirements.lock` зафиксированы версии без хешей. Хеши установленных wheel-файлов
  записаны в `result.json`.
- Исходящий трафик хоста во время репетиции не закрывался. Для неё это и не требуется, а
  для настоящего прогона требуется.
- Один хост и один оператор инфраструктуры.
