# IPVX-BCP02-NET-001-F — первый изолированный Ethernet-опыт

Версия **0.1, proposed / NOT_RUN**. Автор и регистратор: `codex-assistant`.
База исходников: `f467f7ebeb7a2fe8ed108ba6f906fd966735f1a0` — merge PR45.
Этот пакет содержит протокол, декларативный стенд, контракт доказательств и
статическую проверку допуска. **Стенд не создан; runner не реализован; запуска
не было.** Проверка пакета не создаёт namespaces, сокеты, кадры или транзакции.
Принятие PR не разрешает запуск. До отдельного решения владельца опыт запрещён.

## 1. Проверяемый вопрос и граница первого результата

**H1:** на единственном разрешённом пути A—R—B существующие кодек, криптография и
ядро BCP 0.2 смогут доставить DATA и обратные квитанции через настоящие Ethernet
сокеты процессов; отключение R или запрет политики исключит доставку новых
запросов, без IP fallback и без нового message ID при неизвестном исходе.

Это первый **транспортный опыт с синтетическим источником состояния**. Слова ABI
будут получены из принятых контрактов в EVM в памяти, но EL/CL-заголовки и finality
останутся тестовыми. Это не проверка validated-node с живой Sepolia, не полная
сеть BCP-T и не BCP-N. Неизменный wire/profile BCP 0.2 используется под отдельным
тестовым binding; нового поля режима на проводе не вводится. Все результаты
обязаны содержать `state_mode=fixture-state-ethernet`.

В этот опыт не входят: транзакции цепочки, развёртывание контрактов, RPC к живой
цепочке, production, модели, физические линии между гипервизорами, сравнение с IP,
независимые операторы, глобальное присоединение и exactly-once приложения.
Для живого EL/CL потребуется отдельный протокол с реальными адресами контрактов,
runtime hashes, бинарными и TLS-пинами, bootstrap и отдельными разрешениями.
Успех режима F не закрывает эти условия. Старая mesh остаётся отдельным опытом.

## 2. Конкретный стенд, без подключения существующих сервисов

Кандидат — одна новая одноразовая Linux-ВМ либо выделенный тестовый Linux-хост,
пока **не выделенный**. Внутри — три network namespace, три процесса узлов и две
самостоятельные veth-пары. Никаких мостов к host NIC, TAP, VXLAN, GRE, IP-туннелей,
NAT, контейнерной default network, внешних VLAN или скрытого A—B соединения.

```text
namespace A           namespace R                 namespace B
A:a0 <--- veth L1 ---> R:r0   R:r1 <--- veth L2 ---> B:b0
NFT 1                 NFT 3                       NFT 2
endpoint              router                      endpoint
```

Точные имена, MAC, ресурсы и ожидаемые свойства — в [stand.json](stand.json).
Данные передаются `AF_PACKET/SOCK_RAW`, EtherType `0x88B5`, MTU BCP payload 1500.
Это локальный экспериментальный EtherType, не production-присвоение IPvX.
`veth` переносит Ethernet-кадр между парными устройствами внутри Linux, а не
упаковывает его в UDP/IP. После будущего создания это необходимо подтвердить
полным `ip -d -j link`, peer ifindex и inode namespaces, а не рисунком.
Источник: [veth(4)](https://man7.org/linux/man-pages/man4/veth.4.html).

В A/R/B нет адресов IPv4/IPv6, маршрутов и интерфейсов кроме объявленных и `lo`;
`lo` остаётся down. IPv6 autoconfiguration отключается до поднятия veth. Процессы
узлов не могут создавать AF_INET/AF_INET6 sockets, менять namespace или сеть.
Их управляющий канал — только локальные команды START/STOP/барьеры, без payload,
результатов, готовых BCP-кадров или скрытой доставки между узлами. У каждого узла
свои каталог журналов и собственный ключ; чужие приватные ключи недоступны.
Общий kernel поддерживает IP, а host management может использовать Интернет
до опыта. **Отсутствие IP во всём устройстве этот стенд не доказывает.**
Изоляция ресурсов описана в
[network_namespaces(7)](https://man7.org/linux/man-pages/man7/network_namespaces.7.html).

R имеет разные MAC на r0/r1. Нужны два Core/interface-контекста одного NFT в одном
последовательном relay event loop, с явным отображением RX ifindex → контекст,
сессия → egress ifindex и согласованным использованием одного BoundJournal.
Это отсутствующая оснастка, а не уже проверенная возможность PR45. Нельзя
подменить её единым MAC или недоказанным общим состоянием сессий.

Создание и удаление **только новых объектов этого run_id** требует отдельной
подготовки с NET_ADMIN. Рабочий процесс получает лишь необходимые NET_RAW-права
в своём namespace; не получает host NET_ADMIN/SYS_ADMIN. Совпадение имён с уже
существующими объектами — BLOCKED, не повод удалить их. Сам хост, образ и точные
binary hashes пока не назначены; placeholders не являются ресурсным согласием.

## 3. Что ещё требуется реализовать и проверить до запроса запуска

[candidate.json](candidate.json) оставлен незаполненным. Обязательные отдельные
reviewed-артефакты: namespace launcher/cleanup; AF_PACKET transport; двухпортовый
relay; распределённый route-suffix assembler; экспортёр fixture-state и ключей;
ограниченный scheduler/worker; capture verifier; preflight здоровья часов и среды.
Их точные ревизии, SHA-256 и offline validation receipts отсутствуют. Этот PR не
добавляет исполняемый launcher и не выдаёт разрешений на интерфейсы.

Транспорт должен привязываться к конкретному ifindex, отбрасывать
PACKET_OUTGOING как локальную копию, обнаруживать усечение и проверять исходную
длину до BCP decode. Не принимать RX другого интерфейса в чужую сессию.
CAP_NET_RAW, привязка к интерфейсу и MSG_TRUNC описаны в
[packet(7)](https://man7.org/linux/man-pages/man7/packet.7.html).
Эти свойства должны получить собственные offline tests до Linux-допуска.

Каждый процесс подписывает только своим ключом. Origin B передаёт подписанный
ROUTE-суффикс; R проверяет его и добавляет только свою подпись. Удобный
`bcp.build.route`, которому offline harness передаёт все приватные ключи пути,
**не является распределённым runner и запрещён для такого применения**.

Fixture exporter должен создать новый изолированный dataset с реальными
публичными ключами данного опыта и ABI-ответами контрактов в EVM в памяти.
Публичные seeds прежних векторов/примеров не используются как ключи стенда.
Тестовые execution/CL headers получают новые явные синтетические hashes и
время, согласованное с реальными доверенными часами стенда. Повторная выдача
старого header не обновляет timestamp. Dataset и код state-provider фиксируются
до запуска, приватные ключи не включаются в публичную выгрузку. Нельзя подавать
старые timestamps фикстур в реальные часы и объявлять обход STATE_STALE.

В baseline нет patch времени, Attestation-флагов от кадров или live RPC fallback.
Отдельные fault cases меняют только заранее объявленный fixture-bank C/L.
Источник состояния остаётся тестовым даже при корректном исполнении ABI.
Оператор один; разделение процессов/ключевых файлов не создаёт независимость.

## 4. Процедура будущего опыта

Ни один шаг этого раздела сейчас не выполняется. План находится в
[protocol.json](protocol.json); критерии нельзя менять после просмотра результата.

1. **Допуск.** Все компоненты reviewed, source/binary/dataset hashes заполнены,
   стенд и полномочия подтверждены, окно принято, owner ACK привязан к scope
   hash, затем получено отдельное разрешение на запуск. Иначе BLOCKED/NOT_RUN.
   Никаких автоматических merge→run, schedule или production Actions.
2. **Подготовка.** До опыта установить зависимости в одноразовой среде, сохранить
   версии, затем закрыть её egress. Создать только объявленные namespaces/veth
   link-down, запретить autoconfiguration, назначить MAC/MTU. Пока не поднимать link.
   Проверить inventory, маршруты, process capabilities, socket policy, clock
   health и отсутствие bridge/tunnel/физических peer. Несовпадение — остановка.
3. **Наблюдаемость.** До первого link-up и HELLO начать полные captures обоих links, без
   фильтра EtherType и с полным snaplen; одновременно вести событийные журналы
   каждого процесса с monotonic time, интерфейсом, message/packet/session ID и
   решением ядра. Сохранить точные argv без секретов. Не читать чужие outbox.
   Только после подтверждения готовности captures поднять links, повторить
   inventory/policy audit и разрешить HELLO. Непокрытое окно setup — INCONCLUSIVE.
4. **Baseline.** Реальные HELLO/CHALLENGE/CONFIRM на обоих links. Получить
   подписанные ROUTE-суффиксы. Отправить 10 разных запросов по 128 байт A→R→B.
   B после DELIVER/NEW вычисляет SHA-256 полученного plaintext; возвращает
   ACCEPTED и COMPLETED с 32-байтовым результатом. A проверяет результат
   независимо по своим исходным байтам. Это тестовая операция, не LLM.
5. **Контроли.** Выполнить каждый из случаев protocol.json в отдельном case_id.
   Отключение R — barrier до выдачи новых ID; учитывать только post-barrier IDs.
   Нет второго пути и нет ожидания failover. Отзывы относятся к объявленному L
   и доказывают реакцию на fixture-state, не финализацию транзакции Sepolia.
6. **Сохранение.** Остановить узлы и captures, закрыть журналы, проверить полноту
   PCAP и аппаратные/пакетные drop counters, пересчитать hashes всех артефактов,
   вынести выводы с точной ревизией и отрицательными исходами. Только затем
   удалить собственные namespaces/veth по учтённым inode/ifindex. Старые опыты,
   журналы, резервы и подписи не удаляются и не переиздаются.

Baseline и контроль R-off образуют сравнение одной гипотезы. Нет сравнения
производительности BCP/IP; время используется только для ограниченных отказов.
По умолчанию не более 40 логических запросов, 120 DATA attempts, одного
in-flight DATA на сессию, трёх attempts по 5 секунд. На NO_ROUTE/UNKNOWN исходный
message ID, request hash и outbox сохраняются. Автоматический новый ID запрещён.

Рабочая часть ограничена 20 минутами, весь слот с preflight/архивом — 60 минутами;
дополнительно действуют лимиты из stand.json. Нет GPU, моделей, платежей, живой
цепочки или вмешательства в production. Ошибка storage/state/capture не означает
успешную доставку, never-accepted или разрешение повторить опыт автоматически.

## 5. Критерии и доказательства

PASS возможен только при всех обязательных cases и достаточных доказательствах:

- 10/10 baseline запросов дали NEW на B и COMPLETED на A с верным SHA-256;
  каждый immutable/source-signature совпадает на L1/L2; relay не дешифрует DATA.
- При R-off 0/10 новых запросов доставлены/завершены, максимум 3 attempts на ID,
  ограниченный timeout и сохранённый UNKNOWN. Никакого IP fallback.
- Все проверки подписей, политик, C/L, повторов, restart и UNKNOWN дали точный
  заявленный исход; пограничный BCP payload 1500 проходит, 1501 не передаётся.
- На обоих links полные captures, нулевые capture drops, только `0x88B5`.
  Любой ARP/IPv4/IPv6/VLAN/иной EtherType, внешний peer или скрытый путь —
  FAIL_ISOLATION с немедленной остановкой, включая setup до HELLO.
- Новый ошибочный кадр не отравляет последующий корректный sequence; поздние
  ACCEPTED/ERROR не меняют уже сохранённый COMPLETED и его result hash.

Результат не засчитывается по одной stdout-квитанции. Нужны независимые друг от
друга точки наблюдения внутри одного оператора: raw captures links, журналы
процессов и закрытые SQLite snapshots. Это **не независимые операторы**.
Полный набор и правила корреляции — [evidence-contract.json](evidence-contract.json).
Для deliberate bad signature verifier различает объявленный injected frame и
неожиданные повреждения; он не объявляет все captured signatures корректными.

Недостающий/усечённый PCAP, drop, несогласованные часы либо неполная корреляция —
INCONCLUSIVE, не PASS. Неверное поведение протокола при полном evidence —
FAIL_PROTOCOL. Лимит/отмена — ABORTED. Результаты пока `null`; NOT_RUN нельзя
превратить в 0/0 PASS. Частные raw-артефакты сохраняются не менее семи дней,
0700/0600; публичная выборка не содержит ключей, секретов, частных адресов и
реальных пользовательских данных. Новый неякорённый hash не подтверждает личность.

## 6. Проверки этого PR и следующие решения

`python3 -B experiments/bcp02-net-001/checks.py --output /tmp/bcp-net-plan.json`
проверяет только структуру, scope, source pins, изоляционные ограничения,
полноту oracle/evidence и закрытые gates. Никаких namespaces, packet sockets,
эмуляции приложения, сетевого runner или транзакций эти проверки не запускают.
`readiness.py` ничего не исполняет и никогда не выдаёт ready_to_launch=true.
`python3 -B experiments/bcp02-net-001/preserve.py` сверяет прежние исходники,
префикс истории и полный inventory/hash текущего пакета из bundle-manifest.json.
Первая статическая проверка дала 2 отказа из 14 из-за пропущенного allowlist
`tests/bcp/`; причина и hash исходного валидатора сохранены в
[preparation-notes.json](preparation-notes.json). Это ошибка подготовки, не
измерение протокола или сети. Исправление не меняет закреплённые компоненты.

Нужны следующие отдельные решения: принять границу fixture-state опыта и один
Linux-host; согласовать реализацию недостающей оснастки и её ревизию; выделить
одноразовый стенд/слот; подтвердить frozen scope; после успешного preflight —
отдельно разрешить конкретный запуск. Пока все эти launch gates остаются открыты.
История и hashes прежних компонентов находятся в
[preservation.json](preservation.json); старые mesh/strict-native измерения не
переименовываются в BCP network evidence. Никакая инфраструктура этим PR не меняется.
