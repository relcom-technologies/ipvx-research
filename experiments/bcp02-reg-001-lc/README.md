# IPVX-BCP02-REG-001-LC — чтение реестра прогона 6 через лёгкий клиент

Версия **0.1. Статус: выполнен 2026-11-06, исход PASS** ([раздел 7](#7-результат),
[result.json](result.json)). Автор и регистратор: `claude-code-assistant`.
Разделы 1–6 — протокол, принятый в PR69 до запуска; условия и ожидание не менялись, поправки
в разделе 3 отмечены датой. Новое чтение требует нового разрешения владельца.
Машиночитаемая часть — [protocol.json](protocol.json), ожидание — [expected.json](expected.json).

## 1. Зачем

Закрыть R1 из [REG-001](../bcp02-reg-001/README.md) и впервые проверить режим LC
([BCP 0.2-LC](../../docs/proposals/bcp-0.2-light-client/README.md)) на живой сети: адаптер
`lightclient/bcp02/light.py` до сих пор работал только на фикстурах. Одно чтение, ноль
транзакций, без кошельков и ключей.

## 2. Что ожидается и почему не просто S4

В первой версии документов стояло «текущее состояние должно совпасть с S4». Это ошибка
автора: после S4 шла серия R4 — 20 записей `setKeys` для узла A в блоках 12055963–12055987. Поэтому ожидание —
**S4 плюс эта серия**. Его выводит [derive_expected.py](derive_expected.py) из опубликованного
журнала прогона 6, без обращения к цепочке:

| Запись | Ожидание | В S4 |
|---|---|---|
| Узел A (NFT 1) | epoch 21, ключи `0x40e` и `0x40f` | epoch 1, ключи `0x0a` и `0x0b` |
| Ребро A→R | статус 2 | статус 1 |
| Узел R, узел B, NFT 99, ребро R→B, соединение A→B | без изменений | — |
| `allowsEdge` для соединения A→B | ни одно ребро | — |

Ребро A→R перестаёт действовать, потому что каждая смена ключей поднимает epoch узла A
(`BilateralPolicy._effective`), как смена ключей R в S2.

**Предварительная сверка.** 2026-11-06 то же состояние было прочитано через один публичный
RPC в режиме Q (блок 12072638): совпало с таблицей. Это проверка самой таблицы, а не
свидетельство для R1: режим Q ничего не проверяет. Журнал событий там же не показал других
записей в реестр после блока 12055987.

## 3. Порядок чтения

Выполняет оператор на стенде после разрешения владельца. Без production Actions и без
изменений файрвола. Ключи кошельков и `lab.env` чтению не нужны и не читаются.

1. Скачать `helios_linux_amd64.tar.gz` из релиза 0.12.0, сверить SHA-256 с `protocol.json`.
2. Завести пользователя `ipvx-helios` с домашним каталогом `/var/lib/ipvx-helios`.
3. Взять финализированный корень одной эпохи у обоих операторов из `checkpoint_sources`.
   Разные корни — чтение не начинается.
4. Запустить Helios как временный процесс; файл `helios.toml` не создаётся:

   ```sh
   sudo systemd-run --unit=ipvx-helios-r1 --uid=ipvx-helios --gid=ipvx-helios \
     -p MemoryMax=512M -p CPUQuota=50% -p RuntimeMaxSec=3600 \
     -p NoNewPrivileges=yes -p PrivateTmp=yes -p ProtectSystem=strict -p ProtectHome=yes \
     -p ReadWritePaths=/var/lib/ipvx-helios -p Environment=HOME=/var/lib/ipvx-helios \
     /var/lib/ipvx-helios/helios ethereum --network sepolia \
       --checkpoint "$CHECKPOINT" --strict-checkpoint-age \
       --rpc-bind-ip 127.0.0.1 --rpc-port 8545 \
       --execution-rpc https://rpc.sepolia.ethpandaops.io \
       --consensus-rpc https://lodestar-sepolia.chainsafe.io \
       --data-dir /var/lib/ipvx-helios/data
   ```

   Флаг `--load-external-fallback` не передаётся: внешние источники контрольных точек
   остаются выключенными.
5. Развернуть исходники слитого коммита и окружение из `adapters/bcp02/requirements.lock`.
   Дождаться, пока `eth_syncing` вернёт `false`, и сразу один раз выполнить из корня репозитория:

   ```sh
   python3 -B experiments/bcp02-reg-001-lc/lc_read.py --checkpoint "$CHECKPOINT" \
     --helios-tarball "$TARBALL" --helios-binary "$EXTRACTED/helios" \
     --clock-synchronized --output "$RESULT"
   ```

   Поправка 2026-11-06, после запуска. В первой версии здесь стоял путь
   `/var/lib/ipvx-helios/helios`: домашний каталог создаётся с правами 0700, и оператор не может
   прочитать файл, поэтому `$EXTRACTED/helios` — копия из проверенного архива с тем же SHA-256.
   Ожидание `false` перенесено прямо перед чтением: окно длится около 30 с ([раздел 7](#7-результат)).
6. Записать пиковую память процесса (`MemoryPeak`), остановить его, удалить пользователя, данные,
   бинарник и исходники. Результат — отдельным PR, вместе с записью в историю.

Адаптер читает все записи по одному хешу финализированного блока, начиная от точки на 64
блока позади головы, поэтому заодно проверяется поиск предка через EIP-2935.

## 4. Исходы

- **PASS** — ни одного отличия от `expected.json`: R1 закрыт, режим LC принят на живой сети.
- **FAIL_STATE** — любое отличие. Записывается как есть; `expected.json` задним числом не правится.
- **BLOCKED** — адаптер или Helios отказали в чтении. Это дефект совместимости или доступности, а
  не вывод об R1. Новое чтение — после исправления через PR и нового разрешения. Наиболее
  вероятные места: пакетные запросы и `eth_call` с `blockHash` и `requireCanonical`.

Автоматических повторов нет: выходной файл, который уже существует, скрипт не перезапишет.

## 5. Чего это чтение не докажет

- значений S1–S3: они старше окна в 8191 блок и остаются наблюдениями режима Q;
- что прежние ключи A и B были записаны: чтение видит только текущее состояние;
- доступности: источник консенсуса один, его отказ сорвёт чтение, но подделать данные через него нельзя;
- что бинарник релиза собран из коммита `2af9b41`: хеш подтверждает только файл релиза;
- независимого аудита Helios;
- готовности NET-001-L: постоянная служба Helios и окно опыта остаются отдельными условиями.

## 6. Проверка без сети

Из корня репозитория:

```sh
python3 -m pip install -r adapters/bcp02/requirements.lock
python3 -B -m unittest discover -s experiments/bcp02-reg-001-lc/tests -v
```

Тесты запрещают настоящие сокеты и отвечают как Helios поверх `expected.json`. Они проверяют,
что `expected.json` равен выводу из журнала, что простое S4 не проходит, что отличие в одном значении
даёт `FAIL_STATE`, а отказ клиента — `BLOCKED` без вывода о состоянии. Отдельный тест сверяет
опубликованный `result.json` с его хешем в `protocol.json` и с `expected.json`.

## 7. Результат

**PASS, ни одного отличия от `expected.json`.** По разделу 4 это закрывает R1 и принимает режим LC на
живой Sepolia: адаптер `lightclient/bcp02/light.py` впервые работал с настоящим Helios, ответы
проверены доказательствами от корня состояния. Это первая проверка адаптера с Helios вживую, но не
режим постоянной работы.

| | |
|---|---|
| Время чтения | 2026-11-06 00:08:35–00:08:37 UTC, коммит `3135baf` |
| Финализированный блок | 12072858, `0x46570610…f1e1`, возраст при чтении 815 с |
| Начальная точка адаптера | блок 12072794, предок найден через EIP-2935 |
| Контрольная точка Helios | эпоха 359866, `0x290ecce4…c689`, один корень у двух операторов |
| Транзакции и запросы к Helios | 0 и 24 |
| Helios | SHA-256 бинарника `a7f777b4…9180`; пик памяти 12,8 МБ при лимите 512 МБ, CPU 5,1 с, 0 перезапусков |

Блок сверен после чтения: тот же хеш и корень состояния у Tenderly и publicnode, независимых от
этого чтения, и у ethpandaops, который сам служил Helios источником исполнения. Это проверка
блока, а не значений реестра.

### Отступления

- `lc_read.py` запускался дважды. Первый запуск остановился на `PermissionError` при чтении
  бинарника, до единого запроса к Helios, и результата не записал. Второй запуск в том же окне
  получил копию с тем же SHA-256 и дал `result.json`. Чтение было одно.
- `helios --version`, `--help` и `ldd` выполнялись под учётной записью оператора, вне отдельного
  пользователя и его ограничений. Сети и данных эти вызовы не касаются, но обещано было иначе.
- На стенде 3 теста из 10 завершились ошибкой: им нужны журналы прогона 6, которые туда не
  копировались. Семь тестов чтения прошли; в CI проходят все десять.

### Находка: Helios редко готов отвечать

Helios пишет строку состояния раз в 12 с. За время работы таких строк 54, и только в 6 возраст
головы не больше 60 с: только тогда `eth_syncing` возвращает `false`, и только тогда адаптер читает.
Голова сменилась дважды (12072858 → 12072889 → 12072921); единственный полный интервал — 384 с,
возраст доходил до 400 с. Окно для чтения — около 32 с на интервал, ожидания составили 221 с и 347 с.
Чтение прошло при возрасте головы 47 с, запас был 13 с.

384 с равно одной эпохе Sepolia, но причина не выяснялась, а один интервал — малая выборка. В
журнале также 53 предупреждения `inconsistent block history detected: clearing cache`, почти после
каждой строки состояния; ошибок нет, причина не выяснялась. Для [NET-001-L](../bcp02-net-001-l/README.md)
это значит, что обновление снимка «не реже раза в 300 с» с этим источником консенсуса
не выполнимо; условие записано там как открытое.
