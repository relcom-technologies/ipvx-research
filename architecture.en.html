How the network works

A stable ID answers “to whom”. A local route answers “through which neighbor”. A physical link answers “how to transmit the frame”.

From thought to message

Protocol explanation

The model runs on its own machine. The encrypted task and result travel over the network.

Agent ALocal model · stable ID

↓ Ethernet 0x88B5 frames

Relay R1Selects the next neighbor

↓ No IP or DNS in delivery

Agent BIts own model · its own ID

Agent A prepares a task

The recipient is a stable ID. The message receives a signature, expiry time and unique number; its contents are encrypted for B.

This is an interactive explanation, not live network traffic. Actual logs are in the experiments.

Four separate layers

  1. Identity

    The node creates its own keys. Its ID is derived from the public key and persists when its network location changes. Trust and admission are configured separately.

  2. Task

    Agents exchange structured tasks, evidence and results. They do not need website pages for this. Compatible task formats are still necessary.

  3. Routing

    A node receives signed announcements from neighbors and selects the next hop from its local table. The central observer does not relay tasks or assign routes.

  4. Delivery

    In the native experiment, the packet becomes Ethernet frames with EtherType 0x88B5. The MAC identifies a neighbor on the local link; the ID identifies the final agent.

Where IP remains

Machine management, model installation and this website use the existing Internet. Native tasks and route announcements in the experiment use a separate protocol. This tests our own delivery layer in a controlled Ethernet segment.

Connecting independent sites requires physical links or an explicitly disclosed underlay. An IP tunnel between sites would carry IPvX over IP. That can be useful, but it would not demonstrate the removal of IP from the underlying network.

What we retain from IPvX

Self-generated identifiers, separation of identity from location, verifiable contacts and distributed resolution. We add explicit admission, resource bounds and measurable delivery. Human-friendly names remain optional aliases rather than the root of trust.

Next step: a node without TCP/IP

In the current lab, native delivery is separate from IP management. For the next experiment, we propose an image whose kernel itself has no TCP/IP support: the local model communicates with the IPvX service through a Unix socket, and the service sends its own frames through an ordinary network card.
