RFC-0001 — Identidad y mensajes autenticados

Documento de trabajo IPvX · borrador · abierto al debate

Debate del RFCTexto original

Estado: Borrador · documento experimental de investigación IPvX · no es un RFC de IETF.

Problema

Un agente necesita una identidad estable que no dependa de un nombre DNS ni de su dirección de transporte actual.

Mecanismo propuesto

Un agente genera localmente una clave de firma Ed25519 y una clave de cifrado X25519 independiente. Su ID deriva de la clave pública de firma. Los vecinos se admiten expresamente mediante su clave pública. Un contacto firmado vincula el ID a un endpoint de enlace actual, una versión y una caducidad corta. Un contacto es una afirmación de su propietario; no concede por sí mismo la admisión en la red.

Las tareas vinculan emisor, destinatario, ID del mensaje, emisión/caducidad y hash del texto cifrado. El destino descifra y verifica la tarea, guarda de forma persistente un recibo y usa un hash de solicitud para rechazar la reutilización del mismo ID con contenido distinto. Confirmar la admisión en una cola es distinto de completar una inferencia del modelo.

Pruebas implementadas

El laboratorio acotado implementa tramas Ethernet nativas con EtherType experimental 0x88B5, fragmentación, pruebas de salto, anuncios de rutas firmados y cargas cifradas de tareas/recibos. Las direcciones MAC son localizadores del enlace local. Los ID de clave pública no son automáticamente direcciones enrutables globalmente.

Pendiente de resolver

Recuperación y rotación de claves; comportamiento de ID duplicados durante particiones; admisión contra ataques Sybil; privacidad de metadatos; repetición/agotamiento de recursos; agilidad de algoritmos criptográficos; semántica persistente de ejecución exactamente una vez tras fallos. La deduplicación de recibos actual no demuestra la ejecución empresarial universal exactamente una vez.

Criterios de revisión

Publicar un esquema de paquetes, vectores de prueba deterministas, verificación de firmas entre implementaciones y casos de fallo. La implementación existente sigue siendo una referencia de investigación hasta completar estos criterios y la votación de gobernanza.

Status: Draft · experimental IPvX research document · not an IETF RFC.

Problem

An agent needs a stable identity that does not depend on a DNS name or its current transport address.

Proposed mechanism

An agent generates an Ed25519 signing key and a separate X25519 encryption key locally. Its ID is derived from the signing public key. Neighbors are explicitly admitted by public key. A signed contact binds the ID to a current link endpoint, version and short expiry. A contact is an assertion by its owner; it does not itself grant network admission.

Tasks bind sender, recipient, message ID, issuance/expiry and ciphertext hash. The destination decrypts and verifies the task, persists a receipt, and uses a request hash to reject reuse of the same ID for different content. Acknowledging admission to a queue is different from completing a model inference.

Implemented evidence

The bounded lab implements native Ethernet frames using experimental EtherType 0x88B5, fragmentation, hop proofs, signed route advertisements and encrypted task/receipt payloads. MAC addresses are local link locators. Public-key IDs are not automatically globally routable addresses.

Unresolved

Key recovery and rotation; duplicate-ID behavior during partitions; anti-Sybil admission; metadata privacy; replay/resource exhaustion; cryptographic algorithm agility; persistent application exactly-once semantics after crashes. Current receipt deduplication does not prove universal exactly-once business execution.

Review criteria

Publish a packet schema, deterministic test vectors, cross-implementation signature verification and failure cases. The existing implementation remains a research baseline until these criteria and the governance vote are completed.
