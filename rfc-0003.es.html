RFC-0003 — Participación y aprobación por mayoría

Documento de trabajo IPvX · borrador · abierto al debate

Debate del RFCTexto original

Estado: Borrador. La exigencia de mayoría del propietario es vinculante para la admisión al proyecto. Las reglas de arranque detalladas a continuación son una propuesta de implementación provisional, no una afirmación de ratificación comunitaria.

Participación

Cualquiera puede leer los materiales públicos y presentar una propuesta pública. Las propuestas abarcan un RFC, un experimento, un modelo o un cambio del censo. Nunca envíes claves API, claves privadas, conjuntos de datos confidenciales ni endpoints invocables sin restricciones.

Censo y umbral

El censo actual está formado por las cuentas humanas de GitHub incluidas en governance.json. Inicialmente solo contiene al propietario del proyecto, ashkitt: una persona elegible, umbral uno. Es expresamente una fase de arranque. Las instancias de modelos y las cuentas duplicadas no adquieren votos por estar conectadas.

El censo de una propuesta queda fijado al commit de governance.json vigente al abrirla. La aprobación requiere más de la mitad de TODAS las cuentas elegibles, no solo una mayoría de quienes votaron. Abstenerse o no votar no reduce el umbral. La ventana de votación provisional es de 72 horas desde la creación de la incidencia, sin aprobación anticipada. Una mayoría futura puede revisar esta política mediante una propuesta de censo/política y un cambio revisado.

Votos

Las personas elegibles comentan exactamente /vote yes, /vote no o /vote abstain en la incidencia de propuesta. Solo cuentan comentarios autenticados de usuarios GitHub User; se utiliza el último comentario válido de cada persona dentro de la ventana. No cuentan comentarios tardíos, bots, texto libre ni cuentas no elegibles. El workflow programado etiqueta el resultado actual; los comentarios y la pertenencia son públicos. Un workflow fallido no constituye una aprobación.

Controles separados

Una etiqueta de aprobación por mayoría autoriza en principio la admisión a la investigación. No fusiona código, publica RFC, ejecuta modelos ni emite credenciales. Un mantenedor revisa además reproducibilidad, licencias, límites de recursos y aislamiento, y después realiza el despliegue acotado mediante un cambio revisado. El estado del RFC permanece en Borrador hasta registrar la revisión aceptada y la decisión. Una máquina externa puede ejecutar un experimento localmente sin ser admitida en este laboratorio privado.

Cuestiones de gobernanza abiertas

Las apelaciones, la retirada de miembros inactivos, los conflictos de interés, la financiación y cuotas de cómputo, la duplicación de miembros, las suspensiones de emergencia y la autoridad de publicación a largo plazo requieren debate público. Este primer portal no pretende que estén resueltas.

Documento original

Status: Draft. The owner's majority requirement is binding for project admission. The detailed bootstrap rules below are a provisional implementation proposal, not a claim of community ratification.

Participation

Anyone can read the public materials and submit a public proposal. Proposals cover an RFC, an experiment, a model or a roster change. Never submit an API key, private key, confidential dataset or unrestricted callable endpoint.

Electorate and threshold

The current electorate is the human GitHub accounts in governance.json. Initially it contains only the project owner, ashkitt: one eligible person, threshold one. This is explicitly a bootstrap phase. Model instances and duplicate accounts do not gain votes by being connected.

The electorate for a proposal is pinned to the governance.json commit at proposal opening. Approval requires more than half of ALL eligible accounts, not just a majority of those who voted. An abstention or no vote does not reduce the threshold. The provisional voting window is 72 hours from issue creation, with no early approval. A future majority can revise this policy through a roster/policy proposal and reviewed change.

Votes

Eligible people comment exactly /vote yes, /vote no or /vote abstain on a proposal issue. Only authenticated GitHub User comments count; the latest valid comment per person within the window is used. Late comments, bots, prose and ineligible accounts do not count. The scheduled workflow labels the current vote result; comments and membership are publicly inspectable. A failed workflow is not an approval.

Separate gates

A majority-approved label authorizes research admission in principle. It does not merge code, publish an RFC, run a model or issue a credential. A maintainer still reviews reproducibility, licensing, resource limits and isolation, then performs the scoped deployment through a reviewed change. RFC status remains Draft until the accepted revision and decision record are committed. An external machine can run an experiment locally without being admitted into this private lab.

Open governance questions

Appeals, removing inactive members, conflict of interest, funding and compute quotas, membership duplication, emergency suspension and long-term release authority require public discussion. This first portal does not pretend those questions are settled.
